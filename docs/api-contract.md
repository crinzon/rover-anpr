# Актуальные номера: API-контракт

`POST /plates` принимает отдельные наблюдения; `GET /plates` возвращает
`{"plates": [...]}`. `POST` сохраняет прежний ответ `{"status": "ok"}`.
Ключ актуального объекта — `(session_id, track_id)`, а не текст номера.
Обновление одного трека не удаляет остальные. Пустой пакет не очищает
состояние. Порядок элементов списка не является частью контракта.

## Событие

```json
{
  "session_id": "camera-run-unique-id",
  "plates": [{
    "event_id": "globally-unique-id-preserved-on-retry",
    "track_id": 1,
    "plate": "A123AA77",
    "confidence": 0.95,
    "quality": 0.8,
    "frame_id": 123,
    "captured_at": 1794318000.25,
    "position": {
      "x": 0.156,
      "y": -0.25,
      "offset_x_px": 100,
      "offset_y_px": -120,
      "direction": "RIGHT"
    },
    "distance_m": null
  }]
}
```

`captured_at` — Unix UTC seconds, числовое значение, не monotonic и не PTS
видеофайла. Camera вычисляет его для конкретного обрабатываемого кадра по
времени получения декодированного кадра, до JPEG/OCR и очереди отправки.
Это не аппаратная метка затвора RTSP-камеры: такой метки захват пока не даёт.
Для файла это время декодирования на текущей машине; относительный PTS
отдельно передаётся как `video_time_s`. Историческую дату съёмки файла CLI
не восстанавливает. `frame_id` нумеруется внутри сессии Camera.

В ответе GET сохраняются поля события и добавляются:

- `session_id` — позволяет различать одинаковые track_id разных сессий;
- `captured_at` — исходная метка либо null для старого отправителя;
- `received_at` — время обработки события API, Unix UTC seconds;
- `timestamp_source` — `captured_at` или fallback `received_at`;
- `expires_at` — расчётное UTC-время окончания актуальности.

Эти серверные поля нельзя подменить входными значениями.

## Актуальность и порядок

TTL по умолчанию — 2 секунды на каждый трек. При наличии `captured_at`
остаток TTL уменьшается на возраст кадра к моменту приёма события:

```text
remaining = TTL - max(0, received_at - captured_at)
```

Дальнейшее истечение проверяется по monotonic часам сервера, поэтому
перевод системных часов не продлевает уже выданный срок.
В точке `remaining <= 0` наблюдение уже неактуально.

Просроченное событие, а также наблюдение с captured_at не новее текущего,
подтверждается HTTP 200, но не обновляет актуальный трек и SQLite.
Повторный event_id не продлевает TTL. Это канал текущего состояния, а не
интерфейс загрузки архивных наблюдений. Для backfill нужен отдельный API.
Устаревшее событие не может вернуть исчезнувший трек или откатить его номер
и координаты. При исчезновении объекта он удаляется из GET по TTL; отдельное
событие исчезновения пока не предусмотрено.

Для сравнения captured_at и received_at часы отправителя и API должны быть
синхронизированы. Метка более чем на 1 секунду в будущем отклоняется HTTP
422; при допустимом небольшом опережении TTL не превышает 2 секунд от приёма.
Камера и API на одном хосте используют общие системные часы.

## Координаты

`plate_validator.plate_position(box, width, height)` определяет:

```text
cx = (x1 + x2) / 2
cy = (y1 + y2) / 2
offset_x_px = round(cx - width / 2)
offset_y_px = round(cy - height / 2)
```

Единица — **пиксель исходного изображения**, начало — его центр.
X вправо положительный, Y вниз положительный. Смещения округляются до целых
пикселей. Они относятся к рамке именно того кадра, чей captured_at передан.

Для совместимости `position.x/y` остаются нормированными смещениями:
`round(cx/width - 0.5, 3)` и `round(cy/height - 0.5, 3)`.
Нельзя интерпретировать их как пиксели. `direction` — прежняя грубая
горизонтальная зона, не замена координатам.

Если переданы пиксельные поля, обязательны оба; значения должны быть
конечными числами. API проверяет их формат, но без исходного кадра не может
доказать правильность заданных отправителем координат. Формулы Camera
покрыты отдельными тестами, доставка — реальными HTTP-тестами.

## Совместимость и ограничения

Старый отправитель без captured_at принимается. Для него TTL начинается от
received_at, captured_at в GET равен null. Определить задержку доставки
такого события невозможно. Старые нормированные координаты без пиксельных
полей тоже принимаются; API не придумывает отсутствующие смещения.

Сохранены `/history`, `/health`, `/live*`, поля номера и вложенный position.
Отсутствующий session_id по-прежнему возвращает старый JSON status=error.
Некорректные события возвращают HTTP 422 вместо возможного падения SQLite.
Рекомендуется передавать event_id; новый Camera/EventSender делает это.

Актуальное состояние хранится в памяти одного процесса API и исчезает при
его перезапуске. Для нескольких Uvicorn workers/реплик нужен общий store;
текущая конфигурация запускает один worker. Очередь EventSender остаётся
best-effort, её устойчивость к перезапуску не изменена.

SQLite-история дополнена subtype/status; source/receipt timestamps и
координаты в ней не сохраняются. `detected_at` — прежнее время записи API.
Это отдельная будущая миграция, не часть изменения актуального состояния.

## Проверки

`tests/test_api_http.py` запускает настоящий Uvicorn на localhost с
FastAPI и временной SQLite. Для TTL используются управляемые часы, а не
реальные двухсекундные ожидания. Проверяются два трека, независимое
исчезновение, задержка, перестановка событий, повторная доставка,
разделение сессий, legacy-события и доставка координат через EventSender.
Модели, камеры и внешняя сеть тестам не нужны.


## Подтипы и частичные номера

События нового Camera дополнительно содержат `subtype`, `status`,
`confirmed`, `observed_plate` и `character_evidence`. CONFIRMED не допускает
неизвестных символов. По умолчанию GET /plates и /history возвращают только
подтверждённые результаты; `include_partial=true` открывает PARTIAL-записи.
Старые события без статуса остаются совместимыми. В SQLite добавлены
subtype и status, прежние строки сохранены без выдуманного подтипа.
Подробнее: [форматы и накопление доказательств](plate-formats.md).
