# Сравнение настроек ANPR на одном фрагменте

Runner `experiment_anpr.py` запускает четыре конфигурации на одном видео
4096×1860 из 200 кадров:

- 640 / 0.50 — повторный baseline;
- 640 / 0.25;
- 960 / 0.35;
- 1280 / 0.35.

```bash
/home/user/.venvs/rover-anpr-cpu/bin/python -B experiment_anpr.py \
  --input results/smoke-input/front_60s_10s.mp4 \
  --output results/anpr-comparison-01 \
  --device cpu
```

Для повторного запуска нужен новый выходной каталог. Существующий каталог
отклоняется, даже если он пуст. До обработки runner резервирует новый
корень эксклюзивно. Исходные видео, веса и старые результаты не меняются.
Автоматической установки библиотек, скачивания моделей и подключения API нет.

Для каждого варианта используются новые `PlatePipeline` и сессия трекинга.
Три прогревочных вызова на первом кадре исключены из времени обработки.
Все измеряемые прогоны используют тот же SHA256 источника, все 200 кадров
и одинаковые временные метки. Нагрузка от параллельных прогонов отсутствует.
Число CPU-потоков берётся из текущего Torch и сохраняется в manifest;
при необходимости оно задаётся одинаковым для всех вариантов `--threads`.

Основные `process_video.py`, `camera.py`, `full_stand/pipeline.py` не меняются.
Runner вызывает существующий `process_one` с исходным Camera worker.
Временная подмена фабрики `camera.StandConfig` действует только внутри
экспериментального процесса и вызова worker. Это согласует диагностический
конфиг камеры с выбранным pipeline, несмотря на встроенный запрос conf=.5.
После вызова исходная фабрика восстанавливается, включая случай ошибки.
OCR-порог, трекинг и подтверждение остаются исходными.

Перед каждым реальным forward YOLO проверяются фактические `imgsz`, `conf`,
`iou`, `max_det`, а также форма входного тензора. Формы рассчитываются
независимо от `_prepare` и проверяются hook модели:

| imgsz | Фактический NCHW | Число измеряемых forward |
|---:|---|---:|
| 640 | 1×3×320×640 | 200 |
| 960 | 1×3×448×960 | 200 |
| 1280 | 1×3×608×1280 | 200 |

В каждом каталоге `img<size>_conf<percent>` сохраняются `annotated.mp4`,
`report.json`, `detections.csv`, снимки и журналы существующего CLI.
Отчёт дополнен полем `experiment` с выбранными настройками и результатами
проверок. Итоговые `comparison.json`, `comparison.csv`, `comparison.md`
содержат число детекций, подтверждённых строк, время, FPS, среднее время
YOLO/OCR, новые/исчезнувшие строки относительно baseline.

Время YOLO/OCR берётся из существующих `timing_ms.detect/recognize`:
оно включает накладные расходы соответствующих этапов pipeline.
Полное время включает декодирование, отрисовку, экспорт и повторное
декодирование выходного MP4; загрузка моделей и прогрев в него не входят.
Значения с другим числом CPU-потоков или другой нагрузкой не следует
сравнивать как чистое влияние imgsz/conf.

Наличие дополнительных рамок показывает рост числа наблюдений, но не
доказывает рост recall: возможны ложные рамки и дубли. Подтверждённые строки
не являются числом уникальных автомобилей или автоматически правильных
номеров. Поэтому precision, recall и false_positives оставлены null до
ручной разметки. Для проверки нужно просмотреть одни и те же кадры всех
четырёх MP4 и проверить новые подтверждённые строки по исходному видео.

Результаты первого запуска: `results/anpr-comparison-01/comparison.md`.
Тесты без моделей:

```bash
python -B -m unittest discover -s tests -p 'test_experiment_anpr.py' -v
```


## Первый выполненный эксперимент

Все четыре прогона завершены, manifest имеет `status=done`.
Результаты: 299/462/516/615 детекций и 8/10/10/11 подтверждённых строк.
Во всех вариантах ровно 200 обработанных и выходных кадров, длительность
10 секунд; исходные восемь подтверждённых строк сохранены.

Выборочно проверен кадр 197: реальный номер Y273ET797 отсутствует среди
рамок baseline и присутствует у 640/.25 с detector confidence .44458.
Это подтверждает восстановление конкретного пропущенного наблюдения.
Полная оценка precision/recall и ложных подтверждений не выполнена.
Подробности и исходные вырезки —
`results/anpr-comparison-01/review/assessment.md`.

Время baseline в этом запуске 190.65 с против прежних 57.10 с, при тех же
результатах детекции. Однократные замеры не позволяют утверждать, что
увеличение imgsz ускоряет вычисления: для выбора по производительности
нужны повторные чередующиеся прогоны с контролем загрузки CPU.
